# Подробное объяснение Dockerfile.production

## Общая концепция: Multi-Stage Build

**Старый подход (одностадийный):**
- Один образ содержит всё: исходный код, зависимости, инструменты сборки, и результат сборки
- Размер образа большой (включает devDependencies, исходники, и т.д.)
- Сборка происходит при запуске контейнера (медленно)

**Новый подход (multi-stage):**
- Разделение на несколько стадий (stages)
- Каждая стадия - отдельный образ
- Финальный образ содержит только необходимое для запуска
- Сборка происходит при создании образа (быстро при запуске)

## METAADMIN Dockerfile.production

### Stage 1: Dependencies (Стадия зависимостей)

```dockerfile
# Stage 1: Dependencies
FROM node:18-alpine AS deps
```
**Объяснение:**
- `FROM node:18-alpine AS deps` - создает именованную стадию с псевдонимом `deps`
- `AS deps` позволяет ссылаться на эту стадию из других стадий
- Эта стадия нужна только для установки зависимостей

**Почему отдельно:**
- Docker кэширует слои - если `package.json` не изменился, эта стадия не пересобирается
- Ускоряет последующие сборки

---

```dockerfile
WORKDIR /app
```
**Объяснение:**
- Устанавливает рабочую директорию `/app` (вместо `/usr/src/app`)
- Все последующие команды выполняются в этой директории
- Более короткий путь, стандартная практика

---

```dockerfile
COPY package.json package-lock.json* ./
```
**Объяснение:**
- `package-lock.json*` - звездочка означает "опционально"
- Если `package-lock.json` нет, ошибки не будет
- Копируем только файлы зависимостей (не весь код)
- Это позволяет Docker кэшировать слой с зависимостями

**Почему важно:**
- Если исходный код изменился, но зависимости нет - Docker переиспользует кэш
- Экономит время при пересборке

---

```dockerfile
RUN npm ci
```
**Объяснение:**
- `npm ci` (clean install) - устанавливает зависимости строго по `package-lock.json`
- Быстрее и надежнее чем `npm install`
- Устанавливает ВСЕ зависимости, включая devDependencies (нужны для сборки)

---

### Stage 2: Builder (Стадия сборки)

```dockerfile
# Stage 2: Builder
FROM node:18-alpine AS builder
```
**Объяснение:**
- Новая стадия, начинается с чистого образа
- Название `builder` - понятно, что здесь происходит сборка
- Не наследует ничего из предыдущей стадии (кроме того, что мы скопируем)

---

```dockerfile
COPY --from=deps /app/node_modules ./node_modules
```
**Объяснение:**
- `--from=deps` - копирует файлы ИЗ стадии `deps`
- Копируем уже установленные `node_modules` из первой стадии
- Не нужно устанавливать зависимости заново - экономия времени

**Почему не `npm ci` здесь:**
- Зависимости уже установлены в стадии `deps`
- Просто копируем готовые `node_modules`

---

```dockerfile
COPY . .
```
**Объяснение:**
- Копируем весь исходный код
- Теперь у нас есть и зависимости, и код - можно собирать

---

```dockerfile
ENV NODE_ENV=production
ENV GENERATE_SOURCEMAP=false
```
**Объяснение:**
- `NODE_ENV=production` - режим production для сборки
- `GENERATE_SOURCEMAP=false` - не генерировать source maps
- Source maps нужны для отладки, но увеличивают размер сборки
- В production они не нужны - экономия места

---

```dockerfile
RUN npm run build
```
**Объяснение:**
- Собираем приложение СЕЙЧАС, при создании образа
- Результат сборки сохраняется в образе
- При запуске контейнера сборка НЕ нужна - всё уже готово

**Сравнение со старым:**
- Старый: `CMD if [ "$NODE_ENV" = "production" ]; then npm run build && ...`
  - Сборка при каждом запуске контейнера (медленно!)
- Новый: сборка в образе (быстро при запуске)

---

### Stage 3: Runner (Стадия запуска)

```dockerfile
# Stage 3: Runner (production)
FROM node:18-alpine AS runner
```
**Объяснение:**
- Финальная стадия - минимальный образ для запуска
- Начинается с чистого образа
- НЕ содержит исходный код, devDependencies, инструменты сборки
- Только то, что нужно для работы приложения

**Размер образа:**
- Старый: ~500-800 MB (всё включено)
- Новый: ~150-200 MB (только необходимое)

---

```dockerfile
RUN npm install -g serve@14.2.1
```
**Объяснение:**
- Устанавливаем `serve` - легковесный статический сервер
- `-g` - глобально, доступен из любой директории
- `@14.2.1` - конкретная версия (для воспроизводимости)
- Нужен только для раздачи статики React приложения

**Почему глобально:**
- `serve` - это утилита, не зависимость проекта
- Глобальная установка проще для использования

---

```dockerfile
RUN addgroup --system --gid 1001 nodejs && \
    adduser --system --uid 1001 reactjs
```
**Объяснение:**
- `addgroup --system` - создает системную группу (не для входа в систему)
- `--gid 1001` - фиксированный ID группы (для консистентности)
- `adduser --system` - создает системного пользователя (не для входа)
- `--uid 1001` - фиксированный ID пользователя
- `&&` - выполняет обе команды последовательно
- `\` - перенос строки для читаемости

**Почему это важно (безопасность):**
- По умолчанию Docker запускает контейнер от root (UID 0)
- Root имеет полные права в контейнере
- Если злоумышленник получит доступ к контейнеру - он будет root
- Непривилегированный пользователь ограничивает ущерб

**Пример атаки:**
- Если приложение уязвимо и позволяет выполнить команду
- От root: может удалить файлы, изменить конфигурацию, получить доступ к хосту
- От обычного пользователя: ограниченные права, меньше ущерба

---

```dockerfile
COPY --from=builder --chown=reactjs:nodejs /app/build ./build
```
**Объяснение:**
- `--from=builder` - копирует из стадии `builder`
- `--chown=reactjs:nodejs` - меняет владельца файлов
  - Владелец: `reactjs` (пользователь)
  - Группа: `nodejs` (группа)
- Копируем только папку `build` (результат сборки)
- НЕ копируем исходный код, node_modules, и т.д.

**Почему `--chown`:**
- Файлы копируются с правами root по умолчанию
- Непривилегированный пользователь не сможет их читать/изменять
- `--chown` устанавливает правильного владельца сразу

---

```dockerfile
USER reactjs
```
**Объяснение:**
- Переключает контекст выполнения на пользователя `reactjs`
- Все последующие команды выполняются от этого пользователя
- `CMD` тоже выполнится от `reactjs`, а не от root

**Безопасность:**
- Даже если приложение скомпрометировано, оно работает с ограниченными правами

---

```dockerfile
CMD ["serve", "-s", "build", "-l", "3000"]
```
**Объяснение:**
- `CMD` - команда по умолчанию при запуске контейнера
- `["serve", ...]` - exec форма (рекомендуется)
- `-s` - single-page application mode (SPA)
  - Все запросы перенаправляются на `index.html` (для React Router)
- `-l 3000` - слушать на порту 3000

**Сравнение со старым:**
- Старый: `CMD if [ "$NODE_ENV" = "production" ]; then npm run build && npx serve ...`
  - Условная логика, сборка при запуске
- Новый: просто запуск сервера (всё уже собрано)

## FRONTEND Dockerfile.production (Next.js)

### Отличия от metaadmin:

```dockerfile
ENV NEXT_TELEMETRY_DISABLED=1
```
**Объяснение:**
- Отключает телеметрию Next.js (сбор данных об использовании)
- Ускоряет сборку (не отправляет данные)
- Лучше для приватности

---

```dockerfile
COPY --from=builder --chown=nextjs:nodejs /app/.next/standalone ./
COPY --from=builder --chown=nextjs:nodejs /app/.next/static ./.next/static
COPY --from=builder --chown=nextjs:nodejs /app/public ./public
```
**Объяснение:**
- Next.js в режиме `standalone` создает оптимизированную структуру:
  - `.next/standalone/` - содержит `server.js` и минимальные зависимости
  - `.next/static/` - статические файлы (JS, CSS, изображения)
  - `public/` - публичные файлы (robots.txt, favicon, и т.д.)

**Почему три копирования:**
- `standalone` - сам сервер Next.js (заменяет `npm start`)
- `static` - статика, которую раздает Next.js
- `public` - файлы из папки `public/`

**Преимущество standalone:**
- Не нужен `npm start` или `next start`
- Просто `node server.js` - быстрее и легче

---

```dockerfile
ENV PORT=4000
ENV HOSTNAME="0.0.0.0"
```
**Объяснение:**
- `PORT=4000` - порт для Next.js сервера
- `HOSTNAME="0.0.0.0"` - слушать на всех интерфейсах
  - `0.0.0.0` - доступен извне контейнера
  - `localhost` или `127.0.0.1` - только внутри контейнера

**Почему важно:**
- Docker контейнеры должны слушать на `0.0.0.0`
- Иначе Traefik не сможет достучаться до приложения

---

```dockerfile
CMD ["node", "server.js"]
```
**Объяснение:**
- Запускает `server.js` из папки `.next/standalone/`
- Это оптимизированный сервер Next.js
- Не нужен `npm start` или `next start`

## Итоговые преимущества

### Производительность:
- ✅ Быстрый старт контейнера (сборка уже в образе)
- ✅ Меньший размер образа (только необходимое)
- ✅ Кэширование слоев Docker (быстрые пересборки)

### Безопасность:
- ✅ Запуск от непривилегированного пользователя
- ✅ Минимальная поверхность атаки (нет dev-инструментов)

### Надежность:
- ✅ Воспроизводимые сборки (фиксированные версии)
- ✅ Разделение ответственности (каждая стадия делает своё)

### Поддержка:
- ✅ Понятная структура (легко понять, что происходит)
- ✅ Соответствие best practices Docker
